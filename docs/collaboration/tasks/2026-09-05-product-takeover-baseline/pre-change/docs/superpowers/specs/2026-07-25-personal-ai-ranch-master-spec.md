## 0. 文档控制

### 0.1 目的

本文档定义个人 AI 牧场的长期产品方向、领域模型、系统边界、不可破坏的不变量、阶段路线与验收方法。

本文档由以下输入共同形成：

1. 2026-07-25 与牧场主完成的逐题产品访谈；
2. 当前 `main` 的代码、数据库、测试和构建事实，以及已有但需在 P0 重新固化证据的运行界面观察；
3. AgentLoop 从 M1 到 Coding 牧场、CLI 牧工与像素世界的历史设计与实现记录；
4. 牧场主对牛哒智能硬件、云端牧场和商业生态的最新第一手定义。

在牧场主明确确认本文档之前，它是草案，不自动改变现有产品契约，也不授权实现或数据操作。

牧场主确认后：

- 本文档成为长期产品与系统方向的单一事实源；
- 历史 spec、plan 与 impl report 继续作为历史证据，但不再拥有与本文冲突的方向决定权；
- 每个实施阶段必须从本文提取独立的阶段 spec 和精确 plan；
- 才可以创建 Codex 长期实施 Goal，并按本文路线持续执行。

本文只定义仓库内的产品与系统方向，不能覆盖用户/系统指令、法律与平台约束、运行环境权限，或仓库执行与安全协议。仓库内的文档与事实权威层级如下：

| 层级 | 作用 | 冲突处理 |
|---|---|---|
| `AGENTS.md`、协作协议和运行环境约束 | 实施角色、权限、安全、Git 和验证纪律 | 对执行行为具有约束力；与产品方向冲突时必须显式升级，不能静默覆盖 |
| 本长期总 spec | 仓库内产品方向、领域模型、长期不变量和路线 | 在产品方向文档之间冲突时最高 |
| 阶段 spec | 某阶段的已决需求、数据契约和验收 | 不得改变总 spec；发现冲突必须暂停并升级 |
| 实施 plan | 文件范围、步骤、测试和迁移 | 不得发明阶段外决策，也不得扩大授权 |
| Review / impl report / verify log | 当次实施和验证证据 | 记录事实与偏差，不修改需求 |
| 当前代码、数据库和真实运行状态 | “现在实际是什么”的事实 | 实现事实必须如实登记；不能反向覆盖产品方向 |

### 0.2 规范性语言

- **必须**：产品或系统不变量，阶段实现不得自行偏离。
- **应该**：默认方案；偏离时必须在阶段 plan 和报告中说明原因。
- **可以**：允许但非必需。
- **当前事实**：对当前代码的审计结论，不等于未来必须保留的设计。
- **阶段开放决策**：不阻塞总方向，但必须在进入对应阶段前决定。

### 0.3 变更规则

本文是 Living Documentation。

- 产品北极星、唯一目标用户、领域边界、权限原则或架构不变量发生变化时，必须先修改本文并由牧场主确认。
- 实现细节只写入阶段 spec；不把尚未验证的技术选型提前固化进长期总 spec。
- 阶段完成后必须回写路线状态、验收证据与已知偏差；这类事实回写不需要重新确认本文。
- 修改北极星、唯一目标用户、领域边界、权限原则、架构不变量或已确认决策属于规范性变更，必须由牧场主重新确认。
- 不允许代码已经变化而本文继续陈述相反事实。

## 1. 一句话定义

> 个人 AI 牧场是面向 AI 原生独立创作者的、会持续成长的个人多 Agent 工作操作系统：它通过 Coding 教练理解用户真正想要什么，调度可插拔的 AI 牧工持续执行，并把工作推进到可验证、可验收、可复用的真实成果。

Coding 牧场是这一产品母体的第一个旗舰场景，不是最终能力边界。

牛哒是连接个人牧场与物理世界的持续入口，不是牧场本体，也不是独立权限中枢。

## 2. 产品北极星

### 2.1 第一原则

产品的第一价值是产生真实成果。

以下内容都重要，但不能高于真实成果：

- 喂入资料和想法；
- 教练对话；
- 多 Agent 协作；
- 牛与世界的成长；
- 用户打开次数；
- 对话条数；
- 任务运行次数；
- 视觉新奇感。

### 2.2 核心因果链

```text
目标、资料、想法与现场输入
  → Coding 教练理解和教学
  → 共同理解卡
  → 自动组牛与出牧方案
  → Agent Loop 持续执行
  → 真实成果与验证证据
  → 用户或预授权策略验收
  → 营地知识、牛能力与世界成长
  → 下一次工作更快、更可靠
```

### 2.3 要解决的根问题

1. Codex、Claude Code 等工具主要由彼此孤立的对话或任务组成，状态、知识、成果和用户意图难以跨时间复用。
2. 单个 AI 工具可以回答问题或完成局部修改，但通常不能稳定承担从模糊需求、持续追问、计划、执行、验证到验收的完整工作责任。
3. 用户不总在电脑前，灵感、现场信息、补充需求和审批无法持续进入同一个工作系统。
4. 多个 Agent、模型、CLI 和工具缺少统一的状态、权限、记忆、失败恢复和成果治理层。

### 2.4 成功指标

第一北极星指标：

> **每位牧场主每周获得的已验收真实成果数量。**

计入条件：

- 一个成果拥有稳定且不可重复计数的成果 ID 与版本；
- 对应明确的成果契约；
- 有耐久结果；
- 有真实验证证据；
- 经用户或预授权验收策略接受，并记录验收主体、策略 ID 与策略版本；
- 不通过把一个目标机械拆成大量小任务重复计数。

成果新版本、验收撤销、证据失效或成果退回必须保留历史并修正指标；同一成果不能因重跑、换引擎或重复验收而重复计数。首次 onboarding 成果必须由用户本人验收。

护栏指标：

- 从输入到首次成果、从确认到验收的时间；
- 行动成功、失败、退回、取消和永久卡住的比例；
- 每个成果需要用户介入的次数；
- 首次交付通过率与返工轮数；
- 知识、Skill 和牛能力的真实复用率；
- 单个成果的模型、云端和人工成本；
- 用户连续获得真实成果的周数；
- 未解释自动行动、权限越界和隐私事故必须为零。

打开次数、停留时长、对话量、牛的等级与装饰只作为辅助指标。

## 3. 唯一目标用户

### 3.1 目标画像

唯一目标用户是 **AI 原生独立创作者**。

他通常：

- 一个人同时承担产品、Coding、研究、写作、设计、内容和决策；
- 已经熟练使用 Codex、Claude Code、API、CLI 或其他 AI 工具；
- 关心真实成果，而不是只需要聊天或搜索答案；
- 需要多个 Agent 和工具持续协作，但不想自己长期承担人工项目经理工作；
- 需要跨任务、跨时间、跨设备积累知识、偏好和工作能力；
- 愿意理解能力、权限、成本与验证，但不应被迫学习 Prompt 黑话。

### 3.2 明确不是目标用户

- 以“完全不理解 AI 或技术”为主要假设的通用大众用户；
- 专业研发团队、企业组织或多人项目管理者；
- 仅寻找一个代码补全、聊天壳或模型聚合器的用户；
- 只关心虚拟宠物养成、不关心真实工作成果的用户。

产品可以偶然服务这些人，但不能因其需求牺牲唯一目标用户。

### 3.3 第一不可替代价值

牧场不是更换一个聊天窗口，也不是简单把多个模型放进同一界面。

它的不可替代价值是：

> 跨任务、跨 Agent、跨时间地保存目标、状态、知识、证据和成果，让复杂工作能够持续推进、恢复和复利。

## 6. 营地边界

### 6.1 所有权与隔离

- 一个牧场可以拥有多个营地。
- 营地默认隔离。
- 营地必须拥有独立的知识、行动、成果、工作区连接、权限与成长状态。
- 一个营地不能静默读取另一个营地的私有上下文。
- 代码仓库是营地连接的资源，不等于营地本身；一个营地可以连接多个仓库和资料目录。

### 6.2 跨营地桥

跨营地共享必须通过显式、可撤销、可追溯的桥完成：

- 引用；
- 复制；
- 经确认的知识晋升；
- 明确授权的跨营地搜索；
- 用户创建的共享规则。

桥必须记录来源营地、目标营地、内容范围、授权人、时间和撤销状态。

### 6.3 人类协作

- 每个牧场始终只有一位牧场主。
- 未来可以对单个成果、行动或营地开放有期限的评审、确认或只读访问。
- 不建设多人共同拥有、组织层级、团队席位或企业管理系统。
- 临时协作是低优先级能力。

## 7. 牛、驻场与成长

### 7.1 两层牛模型

牛采用两层模型：

**全局牛身份**

- 名字、外观和性格；
- 基础角色和能力方向；
- 经验证的 Skill 与方法；
- 关系、里程碑和全局成长档案；
- 可选默认运行引擎策略。

**营地驻场实例**

- 在该营地的职责；
- 可访问的知识与工作区；
- 具体权限；
- 营地记忆；
- 当前行动、负载与历史表现。

同一头牛可以进入多个营地，但不能自动携带营地私有知识。

驻场必须具有明确生命周期：申请或创建、授权、在场、暂停、离营、权限撤销和历史保留。并发驻留、离营后的营地记忆可见性，以及营地删除后的删除链必须由 P1 数据契约明确；`campId == nil` 不得被解释为“自动拥有所有营地权限”。

牧场主于 2026-07-25 进一步确认：P1 同时定义**可逆归档**与**用户明确确认后的不可逆逻辑删除**。归档不能等同删除；删除不能由 Agent、策略或外部执行器代替用户确认，也不物理删除承载审计关系的 Camp 行。逻辑删除必须停止并拒绝新的营地作用域写入，擦除营地私有敏感正文和内容引用，传播依赖失效/撤权，保留不含敏感正文的最小审计 tombstone。精确静止条件与删除链必须覆盖驻场、桥、Input、Goal、Mission、durable work、Memory、Grant/外部动作、引擎 execution/proposal、事件/outbox 和成果引用；删除 UI 可以后置，但 P1 数据、事务、恢复和测试契约不得延期。

### 7.2 牛不等于模型

- 牛是长期身份。
- 模型、Provider、CLI 和执行环境是可替换运行引擎。
- 更换引擎不能抹除牛的身份和已验证成长。
- 某个引擎独有能力不能伪装成牛已经永久学会。
- 用户可以固定引擎，也可以允许系统按任务动态选择。

### 7.3 双轨成长

**能力成长**

- 以已验收成果、验证记录和复用结果为证据；
- 可以形成版本化 Skill、流程、检查清单或专业能力；
- 营地经验晋升为全局能力前必须提炼、验证并确认；
- 不使用不透明经验值替代真实能力。

**关系与世界成长**

- 共事次数和重要里程碑；
- 外观、住所、动作和故事；
- 营地设施与牧场景观变化；
- 牧场主与牛的长期关系。

权限、模型档位和算力不随等级自动增长。

## 8. 统一输入

### 8.1 一个默认入口

所有来源默认进入同一个“交给牧场”入口：

- 自然语言目标；
- 资料与想法；
- URL 和文件；
- 图片、截图和未来媒体；
- 牛哒语音与其他设备输入；
- 外部服务或扩展推送；
- 熟练用户的直接行动指令。

熟练用户可以使用显式快捷意图：

- 仅记住；
- 整理一下；
- 转成行动；
- 立即开工；
- 关联到指定营地；
- 不进入长期记忆。

快捷意图仍走同一来源、权限和审计协议。

“立即开工”只适用于目标明确、低风险、已具备所需授权的任务，并且系统仍必须先呈现可追溯的最小共同理解卡和成果契约；用户点击或说出“立即开工”可以同时构成对该明确版本的一步确认。只有命中事先由用户明确授权、范围严格匹配且仍有效的自动开工策略时，策略才可以代替当次确认。只要目标、范围、验收、营地归属或权限存在实质歧义，就必须进入教练澄清，不能用快捷意图绕过开工门。

### 8.2 统一输入信封

每项输入至少包含：

- 唯一 ID 与幂等键；
- 原始来源类型、设备与连接器；
- 原始内容或耐久引用；
- 牧场主、作者和时间；
- 候选营地；
- 用户显式意图；
- 隐私和数据处理等级；
- 内容哈希与重复关系；
- 转写、解析和派生内容的来源链；
- 删除、保留与同步状态。

P1 必须为输入定义可恢复状态机，至少覆盖：已捕获、待解析、解析失败、待归属营地、跨营地歧义、待教练澄清、仅存档、已转牧场目标 Goal、已删除与 tombstone。解析和重试必须幂等；无法确定营地归属时，教练必须询问，不能默认写入任一营地。

### 8.3 输入不是命令

捕获、记忆和行动是三个独立门：

```text
捕获内容 ≠ 相信内容 ≠ 写入长期记忆 ≠ 授权执行
```

系统不得把偶然听到、转述、引用或讨论的内容直接当成用户命令。

## 9. Coding 教练

### 9.1 产品地位

Coding 教练是核心产品能力，不只是执行失败后的 `ask_user` 工具。

它同时承担：

1. 帮助用户理解自己真正需要什么；
2. 教用户如何更清楚地表达目标、背景、约束与验收；
3. 解释 Agent 为什么需要某项信息；
4. 把模糊想法转成可执行、可验证的工作契约；
5. 在真实工作结束后复盘表达与协作方式；
6. 经授权记住用户偏好，使长期协作越来越顺畅。

教练不能把负担推给用户，也不能要求用户掌握 Prompt 术语。

Coding 教练是正式系统职责，不预先绑定为某一头牛、营地管家或某个模型。P1 必须先固定稳定的教练 actor、责任归属、审计身份、记忆归属和错误恢复边界；P2 才决定它在产品中显示为独立牛、向导、营地管家或复合角色。无论表现形态如何，教练、规划者、执行者和验证者的责任必须可区分，不能用一个含糊聊天角色代替完整契约。

### 9.2 模糊需求默认先问

- 模糊需求必须先进入教练访谈，不得直接开工。
- 能够从文件、代码、环境或网络查明的事实，系统应该自行调查。
- 会改变产品方向、范围、价值判断或风险承担的决策，必须向用户提问。
- 访谈必须一次解决一个依赖明确的决策，避免一次抛出大量问题。
- 每次提问应该给出推荐答案和理由。

### 9.3 共同理解卡

正式执行前必须形成并确认共同理解卡，至少包含：

- 用户真正要解决的问题；
- 使用场景与目标对象；
- 目标和非目标；
- 交付物；
- 范围与约束；
- 验收标准与验证方式；
- 可使用的资料、工具、工作区和权限；
- 预算、时间或质量策略；
- 已确认假设；
- 尚未解决但允许执行的风险；
- 用户确认记录。

简单任务可以只有几句话；复杂任务允许多轮访谈。

### 9.4 执行中的再访谈

执行中出现新的方向性决策时：

- 只暂停受影响分支；
- 其他不受影响的工作可以继续；
- 形成新的持久问题与版本化决定；
- 更新共同理解卡或出牧方案；
- 不允许执行牛静默替用户做产品决定。

## 10. 组牛、计划与协作

### 10.1 自动组牛

系统根据以下证据提出出牧方案：

- 牛的真实能力和历史验证；
- 营地驻场权限；
- 当前负载和可用性；
- 运行引擎能力；
- 数据边界；
- 预算、成本与速度策略。

用户可以查看选择原因、替换牛、调整预算和修改步骤。

获得相应自治授权的营地可以自动确认出牧方案。

### 10.2 行动板是唯一事实源

- 一个行动同一版本只能有一个规划责任方。
- 一张工作卡始终只有一位负责人。
- 状态变更必须由内核和耐久事件决定。
- 模型自述、聊天内容或 UI 动画不能直接改变事实状态。
- 计划修订必须版本化并记录原因、影响和批准来源。

### 10.3 有边界的 Agent 讨论

牛可以：

- 咨询；
- 提前评审；
- 限轮辩论；
- 请求专业帮助；
- 对失败结果提出修订建议。

讨论必须有轮数与预算限制，结论必须落成以下至少一种耐久对象：

- 决策；
- 交接包；
- 产物；
- 验证记录；
- 工作卡或计划修订。

可以讨论，但不能靠聊天治理。

## 11. 外部 Agent 与运行引擎

### 11.1 控制权

牧场拥有：

- 用户目标和共同理解卡；
- 行动、工作卡与状态；
- 权限和预算；
- 记忆与来源；
- 成果契约与验收；
- 审计、失败和恢复记录。

Codex、Claude Code、API 模型、本地模型和未来 Agent 是可插拔执行牧工。

### 11.2 统一执行协议

所有执行引擎必须能够通过统一协议：

- 领取有边界的工作卡；
- 读取明确授权的上下文；
- 汇报可观察进展；
- 向用户提出持久问题；
- 请求审批；
- 提交结构化交接与成果；
- 明确阻塞或失败；
- 响应取消和紧急停止。

外部 Agent 可以保留专长，但不得绕过牧场私自改变状态、记忆、权限或验收标准。

### 11.3 引擎调度策略

选择顺序：

1. 满足数据、隐私和权限限制；
2. 有能力可靠完成成果契约；
3. 在预算内优化质量、稳定性、速度和成本；
4. 不可用时只自动切换到等价替代；
5. 能力降级必须显式告知。

营地可以设置质量优先、平衡、经济、仅本地或自定义策略。

## 12. 成果、验证与验收

### 12.1 成果契约

共同理解卡或出牧方案必须在开工前定义：

- 交付什么；
- 何时算完成；
- 如何验证；
- 哪些偏差不可接受；
- 谁拥有最终验收权。

### 12.2 真实成果

成果不要求一定是文件，但必须耐久且可检查，例如：

- 通过测试的代码改动；
- 可访问的网站、设计、视频或文档；
- 有来源的研究结论或决策记录；
- 已发送、已发布、已创建的外部对象及回执；
- 可运行自动化；
- 已验证系统状态改变。

完成包至少包含：

1. 实际交付内容；
2. 验证方法与真实结果；
3. 使用的来源与权限；
4. 未完成项与偏差；
5. 已知风险和下一步。

Agent 不能只说“已经完成”。

### 12.3 交付与验收分离

- 执行牛负责交付。
- 测试牛或验证器负责独立证据。
- 验证者不能自行改写成果契约。
- 验证者不得在同一验证步骤中修改被验证成果；如需修复，必须产生新的成果版本并重新验证。
- 系统满足契约后可以标记已交付。
- 最终验收由用户或用户预先授权的验收策略完成。
- 用户可以退回并在原行动、证据和历史上继续修改。

首次、新类型、主观创作、公开发布、付款、删除、外部发送和验证不完整的任务默认人工验收。

独立验证的最低标准：

- 验证 actor 与该成果版本的执行 actor 不同，或由不受执行者自然语言结论控制的确定性验证器完成；
- `VerificationRecord` 固定引用成果契约版本、成果 ID/版本和不可漂移的内容 hash；
- 保存验证方法、命令或规则版本、环境、原始结果、时间、验证者和耐久证据引用；
- 结果只能是通过、失败、阻塞或无效，未知和缺证据必须 fail-closed；
- 成果内容变化、验证器规则变化或依赖证据失效后，原验证自动失效。

P2 的 Coding 金路径至少必须包含一个确定性验证器，例如权威测试、构建、静态检查或可重复的产物校验；模型评语只能作为补充证据，不能单独完成独立验证。

预授权验收必须绑定成果类型、风险范围、验收策略版本、有效期和撤销规则。验收撤销、成果退回或下游证据失效后，相关成果不得继续计入北极星指标。

## 13. 失败、可观测性与恢复

### 13.1 总原则

> 可以自动恢复，但不能隐藏失败；可以修改计划，但不能偷换目标。

### 13.2 分类处理

- 网络超时、限流等临时错误：有限重试，记录原因与下一次时间。
- 确定性代码、工具或数据错误：停止受影响分支，保留证据并定位根因。
- 原计划不可行：规划者提交版本化修订。
- 缺少决策、权限或预算：进入持久提问门。
- App、电脑或云端重启：从耐久状态恢复。
- 降级或替代方案：显式记录并按契约重新确认。

### 13.3 不允许

- 用 `try?`、空数组或默认值把错误伪装成“没有数据”；
- 在缺少知识、工具或权限时静默继续；
- 无限重试；
- 因取消、崩溃或断网把行动永久留在运行态；
- 用 offset、UI 文案或一次性补丁掩盖状态和事务根因；
- 删除诊断证据后宣称问题已经修复。

### 13.4 必须可追踪

关键路径必须能回答：

- 输入从哪里来；
- 教练问过什么、用户决定了什么；
- 谁规划、谁执行、用了哪个引擎；
- 使用了哪些权限和数据；
- 每次状态为何变化；
- 失败在哪里、重试了几次；
- 成果如何验证和验收；
- 记忆和能力如何从证据晋升。

## 14. 记忆与来源

### 14.1 四层记忆

1. **原始来源**
   录音、文字、URL、文件、图片和对话。保留来源、时间、处理历史和删除状态，不直接当成事实。

2. **行动工作记忆**
   当前行动的假设、问答、进展和临时上下文。可以自动形成，行动结束后归档。

3. **营地知识**
   经整理的结论、决策、经验和成果，只在所属营地生效。系统可以建议写入；用户可以授予规则化自动写入。

4. **全局能力与偏好**
   跨营地复用的用户偏好、牛的 Skill 和通用方法。必须有来源、版本、验证证据和撤销能力。

### 14.2 晋升规则

- 自动捕获不等于自动相信。
- 一次行动经验不等于全局能力。
- 原始外部内容不能直接污染长期记忆。
- 推断必须与用户自述和客观行为证据区分。
- 所有长期记忆必须能回到原始来源。
- 用户必须能查看、纠正、撤销、降级或删除。
- 行动过程和原始来源可以实时记录。
- 用户明确确认的事实、偏好与独立资料整理结果，可以凭来源、确认记录和适用范围晋升为营地知识或全局偏好，不必虚构一个工作成果。
- 从行动经验提炼的可复用方法、牛能力与成长必须在对应成果验收后晋升。
- 基于成果的晋升记录必须引用成果、验证与验收版本；成果被退回、撤销或失效时，依赖它的知识、能力和成长进入失效或待复核状态，不得静默继续作为可信能力使用。
- 来源删除必须通过 provenance 图传播删除或失效状态；为了审计而保留的 tombstone 不能保留已要求删除的敏感正文。

## 15. 权限与信任

### 15.1 能力授权模型

权限按三个维度表达：

- 能力：录音、记忆、文件、Shell、联网、发布、删除等；
- 范围：牧场、营地、行动、工作区、文件或外部账号；
- 时间：单次、会话、固定期限或长期。

“全开”是一次授予一组明确、可撤销的权限，不是取消边界。

每项授权还必须记录授权主体、执行主体、目的、数据等级、额度、来源和撤销状态。

以下安全能力必须始终存在：

- 最小必要的事件与审计元数据；
- 权限撤销；
- 紧急停止；
- 失败可见；
- 数据范围检查。

审计不可被静默篡改，但不等于永久保留敏感正文。系统必须区分不可篡改的最小事件元数据、可删除或加密擦除的内容载荷，以及证明删除已经发生的 tombstone。

### 15.2 录音模式

1. **待命**：本地低功耗唤醒检测，短暂循环缓冲，不留存、不上传。
2. **场景记录**：用户通过按键、唤醒词或通勤/会议/灵感模式开启持续记录，有明确设备状态。
3. **持续记录**：用户主动授权后可全天持续记录。

持续记录永远不自动等于：

- 写入长期记忆；
- 创建行动；
- 授予执行权限。

原始音频的默认保留期、端侧处理和加密方案是牛哒阶段开放决策。

三种产品模式与“用户可主动全开持续记录”的方向已经确认；默认模式、具体硬件交互、旁人知情同意、地区法律适用和敏感语音处理必须在 P5 验证后决定。任何留存录音都必须有持续可见的物理状态，且用户能立即静音、删除和撤销设备授权。

## 16. 本地、云端与多设备

### 16.1 系统分工

**云端牧场**

- 持续连接与设备路由；
- 仅对明确同步的 aggregate 和事件类型充当追加式事实源；
- Coding 教练与远程追问；
- 云端安全的资料整理、计划和执行；
- 离线队列与跨设备协调。

**个人电脑**

- 完整牧场世界与工作台；
- 本地代码、文件、CLI、Keychain 与敏感权限；
- 本地执行和真实工作区；
- 高密度验证、审计和验收。

**牛哒**

- 桌面和便携形态；
- 录音豆与物理世界输入；
- 语音追问、简短播报、确认和低风险授权；
- 不直接成为隐形远程控制中枢。

桌面与便携两种产品形态、录音入口和轻交互边界已经确认；具体外壳、核心板复用、验证顺序和默认交互仍由 P5 决定。

### 16.2 用户离开电脑后的行为

电脑离线时，云端可以：

- 转写、理解和继续教练访谈；
- 整理资料与形成共同理解卡；
- 规划；
- 执行已授权的云端安全工作；
- 把本地敏感步骤写入耐久队列。

电脑上线后从队列和事件状态继续，不能重复执行或丢失上下文。

### 16.3 数据分级

每项数据具有独立处理等级：

1. 仅本地；
2. 加密同步；
3. 允许云端执行。

默认仅本地：

- API Key、登录凭据和安全书签；
- 本地工作区与完整文件系统；
- 未经筛选的原始录音；
- 用户标记的敏感资料。

默认允许加密同步：

- 营地和设备状态；
- 行动、工作卡和事件；
- 已确认共同理解卡；
- 经筛选的转写、知识和成果元数据。

云端执行只获取完成明确任务所需的最小数据、用途和时间范围。

```text
同步 ≠ 允许计算 ≠ 允许永久保存
```

### 16.4 多设备一致性

- 云端追加式事件日志是明确同步范围内的权威；本地-only 数据和本地执行事实仍由本地耐久状态拥有。
- 设备离线操作进入本地幂等队列。
- 重试和重复上传不能重复创建行动或执行同一操作。
- 增量资料可以合并。
- 改变目标、验收或权限的冲突必须暂停相关分支并显式处理。
- 禁止用最后写入覆盖历史和决策。

- 共同理解卡和出牧方案；
- 计划、工作卡和修订；
- 代码、文件、日志和验证；
- 权限、成本、错误和审计；
- 资料整理、成果预览和验收。

两层必须读取同一份事实状态，不维护两套业务逻辑。

### 17.2 像素视觉

- 像素风是当前产品世代的正式视觉身份。
- 牛、建筑、地块和动作必须数据驱动，不能烤死在背景图中。

- 数据模型和业务状态不得依赖某张像素图，为未来整体演进保留可能。

### 17.3 真实与生活行为

以下必须由真实事件驱动：

- 规划、工作、测试；
- 提问、审批、受阻；
- 失败、重试、交付、验收和庆祝。

以下可以作为明确的生活行为：

- 闲逛、吃草、睡觉；
- 回牛棚、看风景；
- 无工作语义的社交；
- 使用装饰与设施。

生活行为不得伪造工作进度。点击工作中的牛必须能够回到对应行动、工作卡和最近事件。

## 19. 主动性与注意力

### 19.1 目标受约束的主动性

牧场可以：

1. 主动提醒停滞、权限等待、资料过期和成果待验收；
2. 从新资料、录音、营地目标和历史中提出行动候选；
3. 在命中用户预授权规则时自动建立并执行行动。

牧场不能自行创造用户未选择的长期目标。

### 19.2 四级注意力

1. **仅记录**：普通进展、自动重试、生活行为。
2. **摘要提醒**：低风险自动化完成、新候选和知识整理。
3. **需要处理**：教练问题、审批、验收和计划冲突。
4. **紧急中断**：成本异常、数据风险、不可恢复失败和安全问题。

用户可以按营地、设备和时间设置安静模式、提醒方式、升级时间和合并策略。

系统不得为了活跃度制造紧迫感。

## 20. Onboarding 与外部验证

### 20.1 Onboarding 完成条件

用户必须使用自己的真实需求获得第一个带验证证据的已验收成果。

建议流程：

1. 检测并连接至少一条已有供给线；
2. 根据真实项目建立第一个营地；
3. 交给牧场一个小而真实的需求；
4. 由 Coding 教练形成共同理解卡；
5. 基础执行角色完成工作，首次任务即可使用的系统验证角色独立验证；
6. 用户验收；
7. 展示知识和能力如何沉淀。

示例任务只作为备用，不替代真实成果。

“测试牛”作为世界角色可以在后续成长中解锁，但验证能力不能被游戏化解锁阻塞；从首次真实任务开始，系统必须始终提供独立验证 actor 或确定性验证器。

### 20.2 外部验证

电脑端金路径稳定后立即进入小规模外测，不等待云端与牛哒完成。

**设计伙伴阶段**

- 3–5 位 AI 原生独立创作者；
- 使用自己的真实项目与供给线；
- 近距离观察阻塞、信任与成果。

**首轮验证阶段**

- 扩展到 8–12 位目标用户；
- 连续四周；
- 每人至少 3 个已验收真实成果；
- 至少三周主动回到牧场；
- 能明确感知孤立对话和人工协调减少；
- 出现继续使用或付费意愿。

下载、注册、世界浏览和牛的创建数量不构成产品验证。

## 24. 架构不变量

以下为长期红线：

1. 一个行动同一版本只有一个规划责任方。
2. 一张工作卡只有一位负责人。
3. 成果先耐久、验证后交付。
4. 工作卡只能通过正式终结契约完成或阻塞。
5. 轮数、预算、超时、重试和并发由内核控制。
6. 事实状态来自追加式事件和受约束事务，不信任模型自述。
7. 模糊需求没有用户确认的共同理解卡不得开工。
8. 捕获、记忆、行动和权限是不同的门。
9. 营地默认隔离，跨营地必须显式。
10. 牛身份、驻场记忆、运行引擎和权限彼此分离。
11. 交付与验收分离，执行者不能同时成为最终裁判。
12. 错误不得静默吞掉，恢复不得掩盖根因。
13. 权限必须有能力、范围和时间，可撤销、可审计。
14. 所有具有工作语义的世界状态和动画必须忠实反映执行事实。
15. 用户拥有自己的数据、知识、成果和成长记录。
16. 外部 Agent 必须服从牧场状态与成果协议。
17. 所有输入先进入同一 `InputEnvelope`；只有转为行动的输入才进入牧场目标 / Understanding 模型，且任何入口不得绕过开工门。
18. 模型只能提出建议；真实 ID、依赖、预算、状态与终态由确定性内核控制。
19. 成果、验证和验收必须引用稳定版本与 hash；证据漂移后原结论失效。
20. 所有关键异步转换必须先耐久化，每个 in-flight 状态都必须可收编并到达确定终态。
21. 命令、设备重放、恢复和扣费必须幂等。
22. 敏感工作区、凭据、Shell 与浏览器身份默认留在本地。
23. 牛进入营地必须有显式驻场关系，营地默认隔离。
24. 所有界面和设备只是同一状态的不同投影。
25. 所有具有工作语义的世界动画必须由真实事件驱动；无工作语义的生活动画可以独立存在。
26. 当前测试数据可以经授权重置，但迁移、事件和公开契约必须可回放、可兼容。
