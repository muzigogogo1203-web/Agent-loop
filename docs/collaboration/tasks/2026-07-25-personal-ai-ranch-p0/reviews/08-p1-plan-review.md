### GRDB 7.11.1 and Swift 6 lifecycle feasibility

`Package.resolved` fixes GRDB at 7.11.1, revision
`b83108d10f42680d78f23fe4d4d80fc88dab3212`. Review08 inspected that exact
checkout rather than relying on recalled API behavior. In particular:

- `Configuration.prepareDatabase` runs for the pool writer and every reader;
- setup failure is caught by `SerializedDatabase`, which calls
  `Database.close_v2()`;
- public `DatabasePool.close()` closes the writer and readers with
  `sqlite3_close`;
- deinitialization uses `sqlite3_close_v2`;
- `Database.sqliteConnection`, `Database.isInsideTransaction`,
  `Database.afterNextTransaction`, `DatabasePool.writeWithoutTransaction`,
  and `Database.changesCount` have the shapes required by the frozen Plan.

A standalone temporary probe was compiled against that exact checkout with:

```text
-swift-version 6
-strict-concurrency=complete
-warnings-as-errors
```

It used noncapturing top-level C-compatible callbacks and
`sqlite3_create_function_v2 + Unmanaged.passRetained + xDestroy`, matching the
frozen ownership mechanism. Its final output was:

```text
registrationFailure rc=21 created=1 destroyed=1 deinitialized=1
laterPrepareDatabaseSetupThrow created=1 destroyed=1 deinitialized=1
directPoolClose created=2 destroyed=2 deinitialized=2
busyCloseThenRetry first=SQLITE_BUSY destroyedAfterRetry=1 deinitialized=1
closeV2ZombieFinalRelease preFinalizeDestroyed=0 finalDestroyed=1 deinitialized=1
boundedPointerReuse reuseCount=254 lifecycle=256/256/256
permitAutocommit entry=1 beginImmediate=0 commitCallback=1 rollbackCallback=1
LIFECYCLE_PROBE_PASS
```

These results establish:

- an invalid registration synchronously invokes `xDestroy`; the error branch
  must not manually release the retained context;
- a later `prepareDatabase` setup throw still tears down the installed context;
- a real GRDB pool writer and opened reader each receive one context, and
  direct `pool.close()` destroys both;
- `SQLITE_BUSY` leaves the context live, while successful retry destroys it;
- `sqlite3_close_v2` zombie close delays destruction until final statement
  release;
- repeated pointer reuse is real on this runtime, and destruction can be
  required before each reuse;
- `writeWithoutTransaction` enters with autocommit 1, an owned
  `BEGIN IMMEDIATE` changes it to 0, and GRDB commit/rollback callbacks fire.

This independently closes the concrete GRDB lifecycle impossibility reported
as Review07 `R7-P1-2`. The frozen raw-C ownership route does not depend on the
strong ownership behavior of GRDB `DatabaseFunction`.

The lifecycle probe validates the exact dependency/runtime semantics, not
future implementation correctness. The frozen Plan still correctly requires
implementation tests and source sentinels for provisional publish/reconcile,
duplicate-pointer rejection before the C call, exact-key/cell cleanup, sticky
mismatch handling, and capability sealing.
