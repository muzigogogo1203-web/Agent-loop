# HALT state-flow audit for bounded runtime repair

2026-09-08. Read-only investigation; no tests, builds, processes, samples, Provider/App operations, source edits or Git mutations were performed. This report is the only file written. The latest focused gate observation remains a diagnostic pass, not a behavioral fix.

## Finding

No independent HALT/cooldown state-machine defect is established for the three failed tests. The current code contains the expected dispatch, cancellation and cooldown sequencing. Delayed cooperative task progress is consistent with all three failures, but retained evidence does not identify the executor blocker for these specific fixtures. The separately investigated production blocking-reaper defect is a concrete repair candidate; its existence must not be substituted for proof that it caused every historical HALT failure.

No speculative HALT source change, extra actor removal, earlier transport cancellation, timeout relaxation or global test serialization is recommended by this audit.

## Fixture isolation and actual transitions

`Sources/AgentLoopTestSuite/HaltAndCooldownTests.swift:9-49` creates a UUID temporary database directory and an independent UUID artifact/state root. Each test creates its own Orchestrator, providers and companion. `attachP1F1DispatchContext` (`EngineExecutionStoreTests.swift:1039-1151`) creates a UUID workspace and fresh profile, writes only the supplied database and updates only its supplied companion. `MockProvider` (`Provider/MockProvider.swift:2-71`) keeps script and call count on its own actor. `CallCounter` and `ManualRateLimitClock` (`HaltAndCooldownTests.swift:3200-3230`) are per-instance lock-protected state. No mutable global clock, provider script, dispatch phase, completion registry or database was found connecting these three fixtures.

The compatibility environment is cached per Orchestrator (`Kernel/Orchestrator.swift:11187-11216`) and derives its lock from that fixture's artifact parent (`:11220-11236`). `StateDirectoryLock.swift:133-147` uses nonblocking `flock(LOCK_EX | LOCK_NB)`; this is not a shared indefinitely waiting lock between these UUID roots.

1. `emergencyStopHaltsDispatchAndResumeContinues` (`HaltAndCooldownTests.swift:996-1035`) finishes startup before creating the card, attaches valid dispatch context, stops before any explicit card dispatch, and verifies ready/no run/durable halt. `resume()` (`Orchestrator.swift:12517-12719`) recovers while closed, opens durable running and the supervisor, publishes `.running`, and calls `await reconcile()`. `reconcile()` preserves pending requests across suspension (`:12046-12067`). Its dispatch pass rechecks phase after the database await and after preparation, installs `running` before opening the task gate (`:12250-12313`). There is no demonstrated forgotten post-resume dispatch call. A failed five-second card observation does not distinguish delayed run from a recorded preflight/execution failure.

2. `emergencyStopCancelsRunningBeforeWaitingForPlanner` (`HaltAndCooldownTests.swift:2544-2635`) waits for the runner to start and for a separate planning gate to be entered. `emergencyStop()` suppresses planning, closes dispatch, persists halt and snapshots running entries (`Orchestrator.swift:12321-12399`); it then awaits each bound runtime cancellation before cancelling/joining entry tasks (`:12400-12453`). Planning cleanup happens later (`:12483-12498`). Thus there is no source-level planner-before-runner join inversion. The completion registry's installed cancellation task and gate (`:1820-1917`) and active cleanup task (`:2208-2238`) introduce real asynchronous scheduling points. The already retained observed2 trace proves delay at those boundaries, not a dependency on the fixture planner gate.

3. `rateLimitTriggersGlobalCooldownThenRecovers` (`HaltAndCooldownTests.swift:3135-3198`) uses an independent manual clock and count-switched provider. `run()` starts cooldown from the rate-limit receipt before `runnerFinished` (`Orchestrator.swift:13434-13485`); `runnerFinished` removes the running entry and reconciles (`:13594-13619`). The test already calls `waitUntilIdle()` after its first state observation, so it does not use card status as proof that the later cooldown event has committed. At `rateLimitNow() == cooldownUntil`, the strict `<` guard permits new dispatch (`:12240-12242`). Advancing this fixture clock by 400 ms after the idle gate cannot be invalidated merely by wall-clock delay. No cooldown expiry arithmetic or demonstrated lifecycle race explains the two false observations.

The complete-script fixture omits `artifacts`, but the current `HandoffPayload` decoder explicitly defaults the absent key to an empty array and accepts its nonblank `noArtifactReason` (`Tools/HandoffPayload.swift:54-80`). That familiar historical bug class is not a demonstrated cause here.

## Gate and cross-test checks

The installed gate's `opened`, `canceled` and waiter accesses use one lock (`Orchestrator.swift:573-697`). Registration tests open/canceled while holding that same lock; open publishes `opened` and removes its waiter before resuming outside the lock; cancellation likewise removes the waiter under lock and resumes outside it. This audit found no lost-wakeup window in those operations. Actor admission and resumption still require scheduling (`:700-739`). Removing those scheduling points would change implementation without proving the cause of the retained delay.

One actual shared side effect exists: `emergencyStop` and `shutdown` call `ShellProcessRegistry.shared.terminateAll()` (`Orchestrator.swift:12503,13396`). The registry drains its process-wide PID set and signals it (`Support/ShellProcessRegistry.swift:7-54`). These three fixtures use in-memory Mock/Hanging providers and do not register CLI children; no retained identity join shows a registry signal causing their failure. This is therefore a cross-test coupling to retain in the investigation, not the cause of their pre-cancellation delay.

There are additional synchronous database operations reachable from async work: every `haltTempDB()` calls the synchronous database initializer/migrator (`Database/AppDatabase.swift:3125-3139`); supervisor pump claims synchronously query/write its database (`Work/DurableWorkSupervisor.swift:2350-2383`); execution authority loading also has synchronous steps (`Orchestrator.swift:2514-2540`). The fixture databases are independent, so these are possible aggregate executor pressure, not evidence of a common database lock. No duration/stack evidence identifies them as this run's blocker. Lack of explicit shutdown in the two state-observation tests does not by itself prove a perpetual supervisor pump leak: the pump clears itself when no claim exists and only schedules a next-due timer when a due item exists (`DurableWorkSupervisor.swift:2459-2512`).

## Oracle limit and discriminating verification

The observed2 `false` cancellation result was a real ordering failure: consumption cancellation had not been called when the observer returned false. No oracle change can retroactively turn that failure into a pass.

There is nevertheless a separate proven oracle weakness: `waitUntilCanceled` (`HaltAndCooldownTests.swift:908-923`) returns the current counter after polling, without comparing the cancellation instant with the original deadline. An observer admitted after its deadline can return true for late cancellation. `waitForCard` (`:737-746`) likewise performs a final observation after its nominal deadline. Preserve those limits when describing passing results; current passing assertions establish observed progress, not a strict latency guarantee under all schedules.

If a strict cancellation-deadline claim becomes required, the smallest discriminating oracle regression uses independently controlled instants: cancellation recorded before deadline but observer resumed after deadline must pass; cancellation recorded after deadline but observer resumed after that must fail. Store the first cancellation instant, compare it with the exact observation deadline, and retain their original identities. This is a separate test-oracle change requiring its own reviewed scope, not a proposed fix for the historical false result.

After the independently proven blocking-reaper repair passes its bounded failing-then-passing regression and review, the minimum HALT acceptance evidence is one unchanged ordinary full `swift run RunTests`, with complete output and exit retained. It must include all three parent tests above with zero issues, and all other parent tests must pass. A focused HALT pass alone cannot exercise the historically relevant concurrent workload. Do not change deadlines or serialization to obtain that result. If the full run fails, preserve it and stop acceptance; do not repeat it until a new discriminating cause or diagnostic delta exists.

For a subsequent failing card-state observation, the smallest useful diagnostic delta is fixture/card/execution identity plus wait-start/deadline/final actual status and the corresponding durable engine/error events. That would distinguish absent dispatch, delayed progression and wrong terminal state. Current unbound OSLog records cannot make that distinction by stdout adjacency. The existing installed-gate brackets already cover the cancellation readiness gap and should be reused, not duplicated.

Even a successful post-repair full run supports resolution under that workload and the specific reaper regression. It does not establish that the reaper explains each old HALT issue, a one-second universal guarantee, or App/product acceptance.
