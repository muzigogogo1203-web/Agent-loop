# A1 foundation API and test-seam risk map

Read-only bounded assessment: **the approved A1 scenarios are implementable through current Core/GRDB APIs without a new product decision or broader source allowlist.** The principal risks are transaction replay bypassing redaction hooks, invalid graph joins hidden by optional records, and treating private historical test helpers as reusable symbols. The receipt-CAS test needs an explicit testable seam inside the already allowed new store file. No alternate plan is proposed.

Read the complete `goal-foundation-plan.md` and `goal-output-policy-plan-review.md`; current foundation plan SHA-256 is `c2f0a874bdaf4bfcd1a4d31f8a31c88199d51fd1a92f0b35274a945fe893b4fc`, matching policy approval. Current runtime admission is parent-owned; the historical pending-runtime language in these artifacts is not reinterpreted here. References below are current source line anchors inspected during this assessment.

## Implementation seams and concrete failure risks

### 1. Capture replay must run the original domain receipt validator inside the caller transaction

`InputGoalStore.captureAndEnqueueParsing` currently builds its replay plan/prepared command then opens one pool write. `DomainEventStore.executeCommand(...,database:makeNew:)` is already transaction-taking (`DomainEventStore.swift:21`). Existing-receipt execution validates immutable command hashes and the recorded domain graph before skipping `makeNew` (`:73–110`, `:877–952`). The planned overload can use this directly.

For desktop exact replay after parser progress, validate the carrier/original intent and current graph, then validate/return the original capture receipt through the existing transaction-taking domain path. Do not rerun current input version-1 expectations or require status `.captured`; the historical capture receipt remains valid after the domain projection advances. Do not call `InputGoalStore.input`, `.goal`, `DurableWorkStore.activeWork`, or a pool-backed desktop `snapshot` from inside the existing write/read; use `fetchOne`/queries on the supplied `Database` so one transaction/snapshot remains one transaction/snapshot.

### 2. Both deletion methods need post-replay retention validation within their write

`cancelParsingAndDelete`'s business mutation is at `InputGoalStore.swift:406–408`; this is the atomic redaction hook for new cancellation/deletion. `completeDeletion` currently ignores its mutation's Database parameter (`:665`); use that parameter for its new redaction hook. `executeOrdinary` owns the pool write and returns the domain event-store result (`:693–725`).

On exact replay, `DomainEventStore.executeStrictCommand` returns stored graph metadata before invoking business mutation. Therefore adding only these two mutation hooks is insufficient. Capture the returned receipt, then validate already-redacted carrier/null/safe-receipt integrity **inside the same pool.write**, for the deletion command types only, before returning. Do not call mutating `redact` to repair an inconsistent live carrier on replay; the plan requires `retentionIntegrity` instead of retroactive success. This can be a transaction-taking internal validator in the new store file. Existing legacy inputs without carriers remain valid no-ops.

For rollback tests inject a trigger on the new carrier redaction UPDATE and call the real delete command. Assert input/work/carrier and domain receipt/event/outbox state match their preimages. For exact-replay corruption, retain the original command and deliberately corrupt only new test carrier rows after a genuine tombstone. If newly added immutability triggers block that fixture corruption, explicitly remove only the named new trigger in the isolated DB for the corruption case; never weaken production triggers or original input constraints to make the arrangement possible.

### 3. Reserved IDs must be read and validated, even when their records are optional

`GoalControllerRecord` carries `id`, `campId`, `sourceInputId` (`Domain/GoalController.swift:17`). `CoachSessionRecord` has `goalId` and **optional** `inputId` (`Domain/CoachContracts.swift:25`); sessions have no direct camp column. `CoachTurnWorkInputV1` carries `goalId` and `sessionId` in canonical work JSON (`:330`). Coach enqueue uses kind `.coach`, aggregate type `"goal"`, aggregate ID=goal.id, camp=goal.campId (`Database/CoachUnderstandingStore.swift:1378–1414`).

Read a reserved goal/session if it exists even before input conversion; reject an unrelated record instead of hiding it as absent. After `.goalCreated`, require the fixed goal with exact source input/camp, and require any exposed session to match both fixed goal and source input. Included work must match kind/type/aggregate/camp and validate canonical input bytes/hash plus payload input ID/content hash or goal/session IDs. An aggregate-only query can leak a colliding session's work or silently admit corrupt JSON.

The new SQL reserves `goalId` uniquely but stores `sessionId` only in context JSON. It does not provide a SQL uniqueness guarantee for session reservations. At minimum, validate collisions with actual reserved session records, as the approved graph review requires; do not assume a goalId uniqueness index protects session IDs. If implementation chooses to enforce duplicate session reservation across live carriers too, it can do so within the same new-store transaction using existing context JSON, without inventing a new migration column/index. Record that local invariant explicitly; no broad schema amendment is implied here.

### 4. Receipt-CAS adversarial coverage needs a real accessible primitive

The approved public A1 interface accepts intent for `sealCaptureStage`, but no method accepts a candidate stage receipt. `prepareSubmission` can exercise successful internal append and exact replay, but cannot directly propose a conflicting receipt. The plan explicitly allows transaction-taking internal seal/append primitives. Make the narrow receipt-append primitive package-visible in the new store file if needed for the required conflict test, with the same version/identity/canonical validation as production use. This stays within the approved file and operation scope; it is not a generic future-stage dispatcher. Alternatively corrupt a retained receipt and test validation failure, but do not describe corruption detection as direct append-CAS rejection. No additional public product API or new test-support source file is needed.

### 5. Strict output policy and receipt safety have existing canonical tools

`InputContractValidationV1.requireExactKeys` (`Domain/InputEnvelope.swift:976`) uses dynamic coding keys and detects unknown keys. An enum-keyed container's `allKeys` alone cannot see unknown raw keys. Use the existing strict-key helper in the new domain decoders, require `outputPolicy`'s exact tag/integer keys, and use canonical decode/re-encode equality (`CanonicalContractCoding.swift:48–63`) for persisted payloads. The same path rejects unknown safe-receipt fields instead of silently decoding/dropping a planted text/path key during redaction.

`CaptureInputCommandV1` is Encodable only and its coding keys omit envelope (`InputEnvelope.swift:563`). Store the Codable desktop intent; reconstruct the command and seal `wholeCommandBytes(envelope:payload:)` / hash (`CanonicalContractCoding.swift:31`). Validate A1's exact local-owner actor and non-nil device explicitly; broad existing domain command authorization should not stand in for that narrower desktop identity contract. Selected but unresolved runtime IDs must remain configuration only: no runtime lookup, credential access or effective-mode inference is needed.

### 6. Counts alone do not prove rollback

The historical `p1cInputCounts` example (`InputEnvelopeContractTests.swift:277`) covers input, goal, durable work, domain receipt/event/outbox but only counts. A1's required rollback test must also snapshot deterministic existing-row content/hashes and include both new carrier tables. Stable sorted rows and an explicit field representation in the new test file are sufficient; input/session records are not all Codable, so do not assume a generic JSONEncoder can encode every fetched record. Apply the injected failure at the journal receipt UPDATE after capture, then verify no domain or carrier write survived.

Migration arrangement is already supported: `SQLiteMigrationCompatibilityTests.swift:307` demonstrates `AppDatabase.migrator.migrate(queue,upTo:"v17-p1-engine-coordination")`; the single historical setup correction belongs only in `OutcomeContractTests.swift:406`. No AppDatabase through-version initializer or historical count change is required. The sole writer owns migration RED and current adjacent source, so this map proposes no concurrent edits there.

## Handoff

No material mismatch requires user clarification. The parent should settle the receipt-test primitive visibility and record exact graph/collision invariants during the already-approved implementation review. All other risks above are direct implementations of A1's existing atomicity, replay and retention requirements. A1 completion remains actual captured input, queued parser work and prepared submission with a real capture receipt; locally arranged parsed/converted/session states are test evidence only.
