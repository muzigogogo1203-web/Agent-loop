## Blocking corrections

### 1. P1 — Eligibility must precede claiming a coach turn

`CoachTurnProcessor.runNext()` in `Work/DurableWorkSupervisor.swift:4746` claims the next work of kind `.coach` before looking up runtime/privacy; it cannot target the eligible goal selected by a desktop driver. Its request has no runtime/privacy fields (`Domain/CoachContracts.swift:733`). A driver prechecking one goal and then invoking the current runNext can claim a different, unconfigured/local-only goal. Mapping missing configuration to a Provider failure consumes attempts and can fail the goal; mapping it to cancellation leaves running work for lease recovery. Neither yields the planned harmless persistent “等待配置教练”. The same ownership concern applies to the text-only parser claiming unrelated legacy inputs.

Smallest correction: add exact-work worker entry points using the already existing `DurableWorkStore.claim(workId:workerId:now:leaseDuration:)`, preserving the existing kind-wide API for other callers. Select only carrier-owned due work; atomically recheck context version, camp dispatch/lifecycle, and explicit remote consent before claiming. Recheck dispatch just before Provider start. Missing/unsupported runtime, localOnly, and exhausted control budget remain queued with a separately projected reason and no new attempts. A settings change wakes them. Do not hold a GRDB transaction across credential resolution or a network call.

Add the relevant worker/store files to A's allowlist. Define a tagged unconfigured/selected runtime in context (currently both profile/model are required strings), plus an explicit context-update command with expected version. Define privacy authority: the captured InputEnvelope retains its original privacy level; a separately persisted, explicit consent receipt can authorize future turns, with the effective decision checked at dispatch. Do not silently mutate the immutable capture claim or treat a conflicting context boolean as authorization. Tests: two goals with different eligibility; unconfigured/local-only attempts stay zero across restart; selection change races claim; unrelated queued parsing work is untouched.

### 2. P1 — The verification approval bridge is not an existing callable seam

C says to use the same applicable execution approval controls, but `ApprovalGateHandler` is a card/run tool wrapper. It suspends a card and resumes through the normal card execution lifecycle (`Tools/ApprovalGate.swift:44`, `Database/AppDatabase.swift:5808`). At outcome collection the producing cards are done. Passing a completed producing card to this wrapper either fails its transition or changes execution state, and the resumed model run does not resume a sealed verification attempt. There is no defined approval owner, capability/input hash, dispatch receipt, or resumed-verification handler in C. Directly executing argv because contract confirmation occurred would violate the plan's explicit permission boundary.

Smallest correction: choose and specify one outcome-verification permission seam before C2. Prefer a narrow verification-attempt adapter with an explicit user approval bound to outcome/version/requirement hash/argv/workspace/environment policy, with one-shot dispatch and restart behavior; reuse approval policy and external-operation durability where their contracts support it. If existing card-only grants are reused, identify a real dedicated verification card/run and the exact scheduler lifecycle—never manufacture a run or block a completed producer. This is a necessary bridge; merely saying “same controls” is insufficient. Include denied, expired/stale, restart-after-approval, and ambiguous-dispatch tests. No model call is needed for a deterministic verification process.

Also specify `DesktopCommandVerificationRunner` initialization with a validated resolved workspace/bookmark and attempt identity. `P1DProcessRequestV1` has command/environment/timeout but **no cwd** (`Domain/Verification.swift:261`), so the current proposed conformer cannot obtain it from run(request). An immutable runner context is sufficient; a broad verifier redesign is unnecessary. Its raw evidence must bind that workspace and all process outputs, and declare whether `RecordVerificationCommandV1.evidenceHash` is the hash of the persisted evidence blob or CommandExitVerifier's canonical request/result evidence; these are different bytes.

### 3. P1 — Carrier retention is attached to the wrong deletion path, and immutable JSON cannot also be redacted as specified

`IngestionDeletionStore` handles ingestion/rumination deletion, not InputEnvelope deletion. `CampLifecycleStore` provides lifecycle reads/write authorization, not a general deletion orchestrator. Actual input tombstones are created by `InputGoalStore.cancelParsingAndDelete` and `completeDeletion` (`InputGoalStore.swift:367`, `:648`); `requestDeletion` explicitly excludes `.goalCreated`. There is no currently supported general “logical source/goal deletion” to hook into. The plan's test could therefore pass an ingestion deletion while leaving raw submitted text/correction in the new journal.

Smallest correction: explicitly scope this slice's retention to existing input-deletion commands and archive preservation. Add carrier redaction in the SAME database transaction as both actual input tombstone paths. Fail closed on a tombstoned input in snapshot/reconciliation and never replay its raw request. Do not introduce post-goal permanent deletion to satisfy this plan. When such deletion is implemented later, these carriers are declared dependencies.

Define a redacted representation/state in the migration now: request/context payloads become nullable or a tagged redacted value; preserve original hashes/IDs and safe receipts, separately mark redaction. “Request bytes never change” applies while live, with an explicit terminal retention exception. The currently required context decoder must not turn a successfully deleted input into an unexplained integrity failure. Test deletion after atomic capture but before parsing, after parser completion but before conversion, and restart with a redacted prepared operation. Check that no payload remains in either requestJson or resultJson. This is two existing hooks and a terminal representation, not a new retention engine.

### 4. P2 — Coaching budget accounting has no durable identity or unknown-usage policy

A requires persisting reported tokens and stopping at the “confirmed budget”, but coaching occurs before understanding/contract confirmation. Context contains only a budget number, and the two-table contract defines no per-attempt usage/reservation receipt. Several coach work attempts can follow one already committed user operation; storing one usage value on that operation is neither an adequate identity nor crash-safe accounting. Moreover `TurnResult.usage` defaults to zero (`Provider/LLMProvider.swift:1-20`), so the adapter cannot universally distinguish missing usage from reported zero using this interface.

Smallest correction: define an explicit pre-coach token/turn policy separate from the later mission budget, and persist append-only attempt receipts keyed by workId+attempt in the existing journal representation (no third table is inherently required). Define checked addition, retry accounting, and uncertain completion behavior. Bound the outgoing request as well as the output; a 4,096 output limit alone is not a total-token budget. Either expose usage availability in the Provider adapter contract or conservatively label unavailable/unproven usage and block further automatic turns until a user-approved continuation. Do not claim an exact hard aggregate token ceiling when the Provider cannot supply the required accounting. Add tests for restart after Provider completion but before receipt, duplicate terminal events, integer overflow, and unavailable usage.

### 5. P2 — Immutable multi-stage requests need a concrete evolving-head and completion rule

The journal says requestJson seals all complete command envelopes including expected heads at initial preparation. Submission later consumes a parser-produced head; revision later consumes a worker-produced question/session head; confirmation later consumes a newly proposed understanding head. These heads are not all available when the original user gesture is sealed. The single-prepared-operation constraint also requires a clear end point so a submitted goal does not hold the only slot while waiting for the next user answer.

Smallest correction: seal the original user intent/context/IDs first. Before each dependent command, append its exact typed command/envelope/hash to the operation's stage receipts using a CAS transaction; once sealed, replay it unchanged and use domain receipts to reconcile. A stale sealed command is a visible conflict, not permission to silently reseal against a newer head. Define terminal stages explicitly: submit finishes when the fixed session exists; an answer finishes after its domain commit; a revision finishes after the correction question and exact user answer are committed; automatic understanding-confirmation preparation is a separate system operation. Worker output and UI wait states do not keep an unrelated user mutation slot reserved indefinitely. Define explicit conflict resolution and add restart-at-each-stage tests. This is a small sealed-stage journal, not a generic saga framework.

## Feasible boundaries to retain

- **Revision adapter:** feasible with the current worker outcome enum. Request revision creates a real queued turn; its claimed worker can emit a clearly labeled application-authored correction question; the submitted user correction is then recorded with the real user command. No fabricated claim or fabricated model understanding is necessary. Distinguish the deterministic correction prompt from model speech in history/UI. The following claimed turn uses the real coach. Match the exact sealed nextQuestionId and current persisted heads; do not switch arbitrary unrelated turns to this adapter. A confirmed revision deliberately leaves Goal ready with the old confirmed version until a new version is confirmed; session/head checks must prevent starting the old contract during that visible revision.
- **Atomic mission start:** extracting transaction-taking OutcomeStore helpers and invoking the existing `PlanningDurableWorkLedgerOwner.enqueueMissionPlanning` inside one write is the correct seam. Preflight is outside the transaction; replay skips preflight; exact contract/understanding/context/link checks happen inside it. Preserve historical domain replay semantics after state progression.
- **Return and acceptance:** current returnOutcome restores an achieved goal to active and accepted mission to delivering; applying current card rework afterward inside that same transaction is coherent. Selected done-card head + latest run + handoff hash supplies the missing CAS without a new card revision. Acceptance remains the existing atomic domain operation; memory projection is separately retryable. Preserve accepted history and do not use artifact-viewed UI state as authority.
- **Outcome collection:** actual successful run/producer evidence and immutable manifests are required. Designating an actual final producer is acceptable; claiming a generic system producer is not. New-version transitions listed in C match current OutcomeTransitionPolicyV1. Automatic reconciliation must distinguish a failed verification of the same manifest (explicit verification retry) from a genuinely new completed run/version.
- **Minimality:** keep two carriers, one read model, one owned driver, and the existing mission engine. Do not introduce a new planner, persistence of full Provider raw responses, generic event orchestration, speculative source deletion, or LLM memory distillation. Once the five corrections are incorporated, review only those deltas; reopening the whole product design is unnecessary.
