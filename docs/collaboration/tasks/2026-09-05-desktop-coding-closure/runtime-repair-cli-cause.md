## Code-proved mechanisms

### 1. A blocking process reaper occupies a Swift task worker

`CliProcessBackend.swift:1019–1025` creates `Task.detached` and immediately calls blocking `waitpid(childPID, &rawStatus, 0)`. There is no suspension until the child exits. Detaching a task does not move blocking work onto an explicitly owned blocking queue. The reader tasks (`1067–1095`), stdin task (`1114–1119`), run task (`572–573`), cancellation task (`594–595`), and finalize task (`684–685`) all need Swift task execution to progress.

There is also a launch ordering dependency: the blocking reap task is queued before `SIGCONT` (`1098–1105`). A queued reap can begin while the child is still suspended. With sufficiently many concurrent launches, blocking waits can occupy the workers needed for other executions' continuations and cleanup. This is a concrete forward-progress defect/risk in the implementation, not merely an imprecise timeout.

**Limit:** this source pattern does not establish executor saturation in observed2, nor explain the entire 52.704-second environment interval. That inference needs a controlled regression or direct admitted execution-boundary evidence. The environment capture itself dispatches its blocking operation onto a utility queue (`Support/ShellProcessRegistry.swift:124–145`); its shared result still resumes through Swift tasks (`85–110`). Environment delay can have other causes.

Smallest correction candidate: preserve the single exact-child reap owner, status decoding, EINTR handling, error reporting, and `markExited` publication; move the existing blocking wait to a deliberately owned blocking execution facility and resume a checked continuation once. An alternative is a `waitpid(..., WNOHANG)` async polling owner that yields while no exit is available. Choose one after a focused RED test; do not combine them or alter the grace values. The latter already has an in-repository syscall-result reference at `CliBackendTests.swift:3955–3973`, but its surrounding self-exec helper is not a drop-in product implementation.

### 2. Pre-registration cancellation waits for preparation and then launches anyway

`performCancellation()` first awaits registration (`CliProcessBackend.swift:1196`), then sets the cancellation flag (`1197`), cancels stdin, and signals the group. Pending registration stores its continuation (`1432–1448`). `run()` unconditionally resolves the shared environment (`617`), creates/starts Board (`652–675`), spawns (`680–683`), resumes the child (`1102–1105`), publishes registration (`692`), and opens stdin (`693`). No prelaunch cancellation state is read anywhere on this path.

Consequently, cancellation during a hung preparation cannot complete before preparation resolves; once it does resolve, the canceled execution still creates and resumes a child before it can terminate it. This behavior is source-proved independently of scheduler delay. The normal `killGrace` does not bound this registration wait.

Do not casually fix this by adding `Task.checkCancellation()`: the run task is unstructured and is never retained/canceled. Also do not return fake PID/status/EOF evidence. The current cancellation return type requires evidence about an actual process (`195–223`); a cancellation-before-spawn outcome needs explicit error/result semantics and checked prelaunch cleanup. That is a separate lifecycle repair from changing a reaper, and should receive its own bounded regression and review.

### 3. CLI152 does not deterministically establish its claimed held-pipe condition

The script is `(sleep 0.3) >&2 & printf '%s\\n' 'parent-exited'; exit 0` (`CliBackendTests.swift:272–277`). It has a 300 ms self-expiring holder. The harness does not require a descendant-ready acknowledgement, does not verify parent exit 0, and never waits for the literal `parent-exited` line. Its watchdog begins immediately after `backend.launch` returns, before environment resolution or actual spawn (`1177–1215`, then `292–300`).

The 200 iterations of `Task.sleep(10 ms)` are neither a precise two-second wall deadline nor a deadline relative to parent exit. A delayed launch can consume the entire intended test interval before the scenario exists. Separately, if both the reaper/readers resume after the 300 ms descendant lifetime, the backend can truthfully observe EOF and finish successfully. `drainPipe` checks the actual read result (`2000–2039`); a reader is not required to report an incomplete pipe that has already reached EOF before it observed exit. That possible outcome makes the test's unconditional `.pipeDrainIncomplete` requirement timing-dependent.

After watchdog failure, `cliMechanicsRunOwned` requests real cancellation and joins the consumer (`1220–1224`). `cliMechanicsAssessCleanup` still requires the originally intended `.pipeDrainIncomplete` outcome even on that canceled recovery path (`1371`, `1388–1396`), which explains the second “held pipe cleanup was reported as certain” message. The primary watchdog remains valid; this secondary message is not proof that the backend lied about real EOF/cleanup. Do not suppress the primary failure or change success acceptance to make this run GREEN.

The staged fixture is a generated shebang script which `exec`s `/bin/sh` (`925–930`), not an ordinary direct invocation of the immutable system binary. This introduces a script interpreter/OS policy startup boundary. Its background `sleep` also performs executable lookup through the inherited login environment. No current evidence proves either boundary was CLI152's cause. A mechanics regression must not depend on elapsed policy evaluation or a user's PATH.

## Ownership and correctness that must remain intact

- Execution registration is synchronous before consumption/cancel (`361–386`; fixture `1173–1177`). Preserve this race protection.
- Spawn creates a process group and validates its suspended image before continuation (`926–938`, `991–1012`, `1102–1105`). Keep group identity and authority checks.
- Exactly one owner waits for the exact direct child; do not use `waitpid(-1, ...)`, do not let tests reap the product owner's child, and do not infer reaping from process absence. Existing fixture probes use `waitid(..., WNOWAIT)` for that reason (`1438–1452`).
- Finalization records reaping and each pipe EOF separately, reports incomplete draining, then performs checked group cleanup and Board/config cleanup (`1249–1313`). Preserve error observability and joined cleanup on a failing body.
- There is another source-proved boundedness limitation: `awaitCompletion` races `task.value` against a timer in a structured task group (`1880–1901`). Canceling the task-group child does not cancel or release its wait on the unstructured completion task. A timeout can therefore remain waiting at task-group scope exit. This is not an explanation of the observed successful cleanup, and should not be bundled into a reaper-only change without its own RED test.
